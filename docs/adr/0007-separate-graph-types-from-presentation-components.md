# 저장용 노드·엣지 타입과 표시 컴포넌트는 1:1로 대응하지 않는다

컴포넌트 구조 다이어그램의 실구현 설계에서, 저장용 타입은 구분해야 하지만 표시 컴포넌트는 공유할 수 있는 상황이 드러났다. 반대로 저장용 타입이 없어도 내부 변환 결과를 그릴 표시 컴포넌트는 필요할 수 있다. 아티팩트 스키마는 요소의 의미를 정의하고 표시 컴포넌트는 전달받은 표현 데이터를 그리므로, 두 계약의 1:1 대응을 설계 제약으로 두지 않는다.

## 전제를 깨는 두 사례

### 컴포넌트 구조의 엣지는 타입을 구분하되 RouteEdge를 공유할 수 있다

컴포넌트 구조에서는 컨트롤 요구 규칙에 따라 활성화되는 관계를 일반 관계와 구분해야 한다. 여기에는 분기 케이스 선택과 조건부 on/off가 모두 포함된다. 범용 `default` 엣지에 `activeWhen`을 추가하고 일부 레이아웃·렌더러만 이를 해석하게 하면, 지원하지 않는 조합에서도 조건이 무시된 채 관계가 표시될 수 있다. 별도 저장용 엣지 타입은 이러한 의미와 지원 범위를 명시하기 위한 것이며, 구체적인 타입명은 아직 확정하지 않았다.

그러나 저장용 타입이 다르다는 이유로 표시 컴포넌트까지 새로 만들 필요는 없다. 현재 `default` 엣지는 내부 `route` 엣지로 변환되어 `RouteEdge`로 그려진다. 컴포넌트 구조에서 조건을 가진 관계도 전용 다이어그램 렌더러가 활성 상태·라벨·동작을 구성한 뒤 같은 내부 `route` 엣지와 `RouteEdge`를 사용할 수 있다. 일반 관계와 조건을 가진 관계의 저장용 타입은 구분하면서 표시 구현은 공유하는 구조다.

유지해야 할 동작은 컨트롤 선택값과 경로 도달 가능성에 따른 활성/비활성 표시, 라벨 클릭을 통한 컨트롤 값 역산·적용, 라벨 호버 시 간선 점등과 변경 미리보기다. 이 의미 해석과 상호작용 정책은 컴포넌트 구조 렌더러와 관련 상태·라벨 로직이 담당한다. 별도 엣지 타입은 새 디자인이나 동작을 도입하기 위한 것이 아니며, 선과 라벨을 그리는 컴포넌트의 재사용과 충돌하지 않는다.

### 저장하지 않는 결정 노드도 표시 컴포넌트가 필요하다

스파이크의 `projectDecisionNodes`는 입력과 출력에 같은 `DiagramGraph`를 사용하고, 생성기가 결정 노드와 분할 간선을 아티팩트에 저장한다. 실구현에서는 컴포넌트 관계·컨트롤·원래 활성 조건을 SSOT로 두고, 결정 노드와 그에 따른 분할 간선·포트 참조·구간별 조건은 저장하지 않고 내부에서 계산하기로 했다.

이때도 결정 노드를 그리는 컴포넌트는 필요하다. 표시 컴포넌트를 구현한다는 이유로 아티팩트 스키마에도 결정 노드 타입을 추가할 필요는 없다. 일반 다이어그램에서 결정 노드를 직접 작성하고 저장하는 기능은 별도의 저장 계약 결정이며, 표시 구현은 재사용할 수 있다.

## 결정과 경계

- 저장용 스키마와 내부 표현 모델의 계약을 구분한다. 변환 결과가 저장용 `DiagramGraph`를 그대로 따라야 한다는 전제를 두지 않는다.
- 여러 저장용 타입을 같은 내부 표시 타입과 컴포넌트로 변환할 수 있으며, 저장용 타입에 없는 요소도 내부에서 합성해 표시할 수 있다. 표시 컴포넌트의 분리는 실제 표현·상호작용 계약을 기준으로 판단한다.
- 표시 컴포넌트를 공유해도 저장용 타입의 의미와 검증 책임은 유지한다. 그릴 수 있다는 이유만으로 의미를 해석하지 못하는 레이아웃·렌더러 조합을 허용하지 않는다.
- [ADR 0003](0003-layout-renderer-one-to-one-contract.md)의 레이아웃과 다이어그램 렌더러 간 1:1 계약은 유지한다. 그 계약과 렌더러가 사용하는 하위 노드·엣지 표시 컴포넌트의 재사용은 다른 축이다.

## 후속 리팩터링

실구현에서 다음 결합을 정리해야 한다.

- 컴포넌트 구조의 저장용 엣지 타입과 지원 조합 검증을 설계하고, 일반 관계와 조건을 가진 관계가 같은 `RouteEdge`를 사용할 수 있도록 의미 해석과 표시 데이터 구성을 분리한다.
- 결정 노드 투영을 저장용 스키마에 종속되지 않는 내부 모델로 옮긴다. 표시 컴포넌트의 존재를 저장용 노드 타입의 지원 여부와 연결하지 않는다.
- 다른 노드·엣지에도 같은 전제가 남아 있는지 검토한다. 예를 들어 `MessageEdge`와 `RouteEdge`는 모두 `BaseEdge`와 `EdgeLabelRenderer`를 사용하지만 입력과 라벨 표현 계약이 다르다. 메시지의 화살표·점선은 이미 상위 변환 함수에서 결정한다. 경로·라벨 계산과 표시 책임을 정리하면 공통화할 여지가 있으나, `message` 타입을 유지해야 한다는 사실만으로 전용 표시 컴포넌트를 유지하거나 폐지하지 않는다. 현재 구현을 그대로 교체하거나 즉시 통합한다는 결정은 아니다.

리팩터링은 스파이크에서 확정한 디자인과 기본 동작을 보존해야 한다. 배치 알고리즘 등의 변경도 별도 합의 없이 포함하지 않는다. 이 ADR은 결정과 후속 작업을 기록하며, 현재 코드는 변경하지 않는다.
